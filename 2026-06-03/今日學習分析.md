## 四、概念鞏固：用自己的話解釋

**Q1：useLocalStorage 為什麼不用 onMounted 讀取 LocalStorage，而是在 ref() 初始化時讀？**

A：`onMounted` 是 Vue 生命週期的掛載後階段——這時元件已經完成第一次 render。若在 `onMounted` 才讀取 LocalStorage，Vue 會先用 `defaultValue` 渲染一次，`onMounted` 執行後再用 LocalStorage 的值更新，觸發第二次 render（閃爍）。  
直接在 `ref()` 初始化時讀取，`ref` 的初始值就是持久化的值，Vue 第一次 render 就是對的。  
這也是 Composable 可以在 `setup()` 頂層同步執行的優勢——不需要等待生命週期。

**Q2：`useLocalStorage<T>` 回傳 `Ref<T>` 而不是 `Readonly<Ref<T>>`，這個設計決策是怎麼來的？**

A：看使用端需求。`useLocalStorage` 的設計意圖是：你給它一個 key，它給你一個「自動同步到 LocalStorage 的 Ref」。使用端直接對這個 Ref 寫入，就會自動持久化——這是它的核心價值。  
如果回傳 `Readonly`，使用端就無法直接改值，每次都要呼叫特定的 setter 函式，讓介面變複雜。  
對比 `useAsyncData`：data 的更新必須經過 `execute()` 這個入口，才能保證 loading/error 狀態一致性，所以回傳 readonly 是必要的。  
**原則：封裝邊界在哪裡，使用端需不需要寫入，決定要不要 readonly。**

**Q3：`parseJSON<T>` 為什麼要獨立出來，不寫在 useLocalStorage 裡面？**

A：有兩個原因。  
一是**單一職責**：`parseJSON` 的工作是「安全地把字串變成 T 或 null」，和「持久化 Ref 管理」是兩件不同的事。獨立出來後，邏輯邊界清晰。  
二是**可測試性**：`parseJSON<T>` 是純函式（輸入字串，回傳 T 或 null，無副作用）。三個風險點（null / SyntaxError / 型別不符）都可以獨立寫 unit test 驗證。如果混在 Composable 裡，測試 Composable 就需要 mock localStorage，複雜度大幅提高。

## 五、今日知識地圖

```
useLocalStorage<T> 設計地圖
│
├── 設計動機
│   └── W3 useTasks 的持久化邏輯 → 重複 × N → 提取為通用 Composable
│
├── API 設計（使用端視角優先）
│   ├── 輸入：key: string, defaultValue: T
│   └── 輸出：Ref<T>（可寫入，自動同步到 localStorage）
│
├── 初始化策略
│   ├── SSR 安全：typeof window !== 'undefined'
│   ├── parseJSON<T>：隔離三個風險點
│   └── 直接在 ref() 賦值（非 onMounted，避免閃爍）
│
├── 寫入回路
│   └── watch(data, () => localStorage.setItem(key, JSON.stringify(val)), { deep: true })
│
├── 與 useAsyncData 的設計對比
│   ├── useAsyncData → Readonly<Ref<T>>（Composable 掌控更新，封裝三態管理）

│
└── Composable 分層架構
    ├── 基礎設施層：useEventListener（事件管理）
    ├── 持久化層：useLocalStorage（資料保存）
    ├── 非同步層：useAsyncData（網路請求）
    └── UI 邏輯層：usePagination（分頁計算）
```
