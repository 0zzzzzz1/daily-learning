## 概念鞏固：用自己的話解釋

**Q1：為什麼 checkbox 不能用 `v-model="task.done"` 而要用 `:checked + @change`？**

**A：**

`v-model` 是雙向綁定的語法糖，它等同於：
```vue
<input :value="task.done" @input="task.done = $event.target.checked" />
```

問題在於 `task.done = ...` 這一行——它直接修改了 `filteredTasks` 中任務物件的屬性。
而 `filteredTasks` 是 `computed` 回傳的結果，計算結果不應被外部 mutate。

正確做法是透過 `toggleTask(task.id)` 通知 `useTasks`，由 Composable 去更新 `tasks.value`，再讓 `filteredTasks` 根據新的 `tasks` 自動重算。這維持了「單向資料流」：UI → 方法 → State → Computed → UI。

---

**Q2：三種空狀態為什麼要分開處理，而不是統一顯示「沒有任務」？**

**A：**

兩種空狀態的**使用者心理模型不同**：

1. **無任務（totalCount === 0）**：使用者還沒新增任何東西，需要引導行動（Call to Action）。
2. **篩選無結果（totalCount > 0，filteredTasks.length === 0）**：使用者**知道有任務存在**，只是被篩選條件擋住了。此時顯示「沒有任務」會讓使用者困惑——「我明明有任務啊？」正確的做法是提示「目前篩選條件下沒有結果」，並提供解除篩選的按鈕。

這是「使用者語意模型」和「系統狀態語意」相互對齊的設計決策。

---

**Q3：`clearDone()` 的邏輯應該放在 `useTasks.ts` 還是 `TaskList.v2.vue`？**

**A：**

應放在 `useTasks.ts`。理由：

- `clearDone` 修改的是 `tasks`（State），這是 Composable 的責任範圍
- 元件只應呼叫方法，不應直接操作 State（即使是透過計算後的 ref）
- 放在 Composable 的好處：其他頁面複用 `useTasks` 時，也能使用 `clearDone`，不需要重複實作

如果放在元件中：
```vue
<!-- ❌ 不應該這樣做（直接修改 Composable 的 State）-->
function handleClearDone() {
  tasks.value = tasks.value.filter(t => !t.done) // 直接操作 tasks，破壞封裝
}
```
這樣等於繞過了 Composable 的封裝，讓「誰有權修改 State」變得不清晰。
