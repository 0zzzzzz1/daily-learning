## 四、概念鞏固：用自己的話解釋

**Q1：為什麼 `useAsyncData` 要在每次 `execute()` 呼叫時都新建一個 `AbortController`？**

A：因為每次新請求開始前，要能「取消上一個還在進行的請求」。如果只建立一個 AbortController 並在 `onUnmounted` abort，那在元件存活期間 userId 改變時觸發的多次 fetch，舊請求仍會繼續執行並在回來後覆蓋新資料。每次 `execute()` 新建 AbortController 後，先 `abort()` 上一個，再把新 controller 存起來作為下一次 `abort()` 的目標——這形成了一個「最後一個勝出」的機制。

**Q2：`readonly(data)` 和 `data` 直接回傳有什麼本質差異？**

A：`readonly(data)` 回傳一個唯讀代理，使用端嘗試 `user.value = xxx` 時，Vue 在開發模式下會警告，生產環境下靜默失敗。這確保 `data` 的更新路徑**只有** Composable 內部的 `execute()`。若直接回傳原始 ref，使用端可以繞過三態管理直接修改 `data`，破壞 loading/error 與 data 的一致性（例如直接設 `data.value = result` 而不重置 `loading`）。`readonly` 是 Composable 的封裝邊界。

**Q3：`fetch` 被 abort 時拋出的 AbortError，如果不過濾掉，用戶會看到什麼？**

A：AbortError 會被 `catch` 捕獲，然後 `error.value = String(e)` 或 `e.message`，UI 會顯示「The operation was aborted.」或類似的錯誤訊息。但這根本不是真正的失敗——這只是「上一個請求被新請求主動取消了」。顯示這個錯誤會讓用戶困惑。過濾的判斷是 `instanceof DOMException && e.name === 'AbortError'`，過濾後直接 `return`，不更新 `error.value`。

## 五、今日知識地圖

```
useAsyncData<T> 設計地圖
│
├── 抽取動機（為什麼要有這個 Composable）
│   └── 每個 API 呼叫都有相同的三態樣板 → 重複 × 3 → 提取訊號
│
├── API 設計（使用端視角優先）
│   ├── 輸入：fetcher(signal: AbortSignal) => Promise<T>
│   └── 輸出：{ data, loading, error, refresh }
│       ├── data: Readonly<Ref<T | null>>   ← readonly 封裝邊界
│       ├── loading: Readonly<Ref<boolean>>
│       ├── error: Readonly<Ref<string | null>>
│       └── refresh: () => void
│
├── 三態管理
│   ├── 載入中：loading=true, error=null, data=舊值（不清空！）
│   ├── 成功：loading=false, error=null, data=T
│   └── 失敗：loading=false, error=string, data=null（或保留舊值）
│
├── Race Condition 防禦
│   ├── 每次 execute() 建立新 AbortController
│   ├── 建立前先 abort() 上一個
│   ├── fetcher 接收 signal，讓請求可感知取消
│   └── 回調中檢查 signal.aborted，拒絕過期回應
│
├── AbortError 過濾
│   └── instanceof DOMException && name === 'AbortError' → 直接 return
│
└── 生命週期整合
    └── onUnmounted：abort 進行中的請求（清理資源）
```
