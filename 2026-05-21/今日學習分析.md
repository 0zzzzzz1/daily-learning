## 二、學習前 vs 學習後對照

| 概念 | 學習前認知 | 學習後認知 | 理解提升 |
|------|-----------|-----------|----------|
| `EventTarget` vs `HTMLInputElement` | 「event.target 就是 input 元素」（隱性假設）| `EventTarget` 是基底型別，不含 `.value`；需要 `as HTMLInputElement` 或 `instanceof` 守衛才能縮窄 | ⬆⬆⬆ 顯著 |
| `InputEvent` vs `Event` | 「不知道 InputEvent 型別」| `InputEvent` 繼承自 `UIEvent` → `Event`，比 `Event` 更精確；但 `.target` 仍是 `EventTarget` | ⬆⬆ 明顯 |
| `FocusEvent` 型別鏈 | 「blur 事件的型別？直接用 Event 吧」| `FocusEvent` 繼承自 `UIEvent`；`onBlur` 應標注為 `FocusEvent`；存取 `.target.value` 同樣需要 `as HTMLInputElement` | ⬆⬆ 明顯 |
| `$attrs` Fallthrough | 「未宣告的屬性就消失了吧」| Vue 預設把未宣告的 attrs 套到根元素；設 `inheritAttrs: false` 後手動用 `v-bind="$attrs"` 控制套用位置 | ⬆⬆⬆ 顯著 |
| 表單狀態設計 | 「每個欄位一個 ref」| 結構固定的表單適合 `reactive` 物件；搭配 Composable 封裝；用 `keyof` 做型別安全的迴圈驗證 | ⬆⬆⬆ 顯著 |
| CustomSelect 泛型 | 「不確定元件怎麼做泛型」| `generic="T extends string | number"` 讓 defineProps 和 defineEmits 共享型別參數 T | ⬆⬆ 明顯 |

## 四、概念鞏固：用自己的話解釋

**Q1：`inheritAttrs: false` 和 `v-bind="$attrs"` 為什麼要一起使用？**

> 當你在 `CustomInput` 用 `<div>` 包住 `<input>` 時，Vue 預設會把父元件傳入的所有「非 props / 非 emits」的屬性套到**根元素（div）**。但是 `inputmode`、`autocomplete` 這些屬性應該套到 `<input>` 上才有意義。
>
> 解法是：先用 `defineOptions({ inheritAttrs: false })` 告訴 Vue「我自己來控制」，然後在 `<input>` 上加 `v-bind="$attrs"` 手動指定位置。缺一不可——只設 `inheritAttrs: false` 但忘記 `v-bind="$attrs"`，那些屬性就完全消失了。

**Q2：表單狀態為什麼選 `reactive` 而不是多個 `ref`？**

> 表單欄位有自然的「歸屬感」——它們都屬於同一個表單，放在一個物件裡讓結構清晰。而且 `reactive` 不需要 `.value`，在迴圈驗證時 `form[key]` 比 `formRef.value[key]` 更直觀。
>
> 更重要的是：`errors` 物件和 `form` 物件的 key 可以對齊（都用欄位名），搭配 `keyof LoginForm` 就能做型別安全的迴圈驗證，不需要一個一個手動 if。

**Q3：`useLoginForm` 回傳 `form` 和 `errors`，需要 `toRefs` 嗎？**

> 不需要。`form` 本身就是 `reactive` 物件，`errors` 也是。使用端寫 `form.username`、`errors.password` 就能直接存取，不需要解構——所以不需要 `toRefs`。
>
> 如果使用端非要解構（例如 `const { username } = form`），這就會失去響應性。這是 `reactive` 解構陷阱的老問題。設計上就避免提供解構用法，回傳整個物件。
