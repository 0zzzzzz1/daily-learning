**今日核心問題解答**（W4 Day 2 帶入的問題）：

> 當 Composable 的回傳值包含「函式」和「響應式資料」時，是否需要對整個回傳物件做 `toRefs`？

**答**：不需要，也不應該。`toRefs` 的職責是「讓 `reactive()` 物件的屬性可以解構後仍保持響應性」。函式不是響應式資料，不需要 `toRef`；而如果使用的是個別 `ref()` 而非 `reactive()`，也完全不需要 `toRefs`。正確模式：`{ ...toRefs(reactiveState), method1, method2 }` 或 `{ ref1, ref2, method1, method2 }`。

## 概念鞏固：用自己的話解釋

### Q1：toRefs 的正確使用時機是什麼？

`toRefs` 只應該用在一個情境：**你用了 `reactive()` 建立了一個物件狀態，而你需要讓使用端（或元件模板）可以解構它，且解構後的變數仍然保有響應性。**

如果沒有這兩個條件（reactive 物件 + 需要解構），就不需要 toRefs。

**三個不需要 toRefs 的場景**：
1. 你用的是個別的 `ref()`，而不是 `reactive()`
2. 你用了 `reactive()`，但使用端不需要解構（直接 `state.xxx` 存取）
3. 你想轉換函式——函式不是響應式資料，不應該被 toRef

### Q2：為什麼 `toRefs({ count: ref(0) })` 會出問題？

`toRefs` 期望的輸入是 `reactive()` 返回的 `Proxy` 物件，而不是普通的 JavaScript 物件。

當你傳入一個普通物件 `{ count: ref(0) }` 時，`toRefs` 會對每個屬性做 `toRef(plainObj, 'count')`，而這個操作會建立一個「指向 plainObj.count 的連動 ref」。問題是：

- `plainObj.count` 本身已經是一個 `ref`（RefImpl 物件）
- `toRef(plainObj, 'count').value` 會返回 `plainObj.count`，也就是原本的 ref
- 結果：你取到的是 **ref 的 ref**——需要 `.value.value` 才能拿到真正的值

這是「雙層包裝」的陷阱，實務上幾乎不會想要這個結果。

### Q3：useLifecycleLogger 的 hookCounts 為何不需要 toRefs？

```ts
// 使用端
const { logs, hookCounts, clearLogs } = useLifecycleLogger()
```

使用端解構了 `hookCounts`，但它是一個 `reactive` 物件，解構後不會失去響應性嗎？

**不會**，因為解構的是「整個 `hookCounts` 物件的參考」，而不是解構 `hookCounts` 的**屬性**。

```ts
// 解構物件本身的參考 → 保持響應性 ✅
const { hookCounts } = useLifecycleLogger()
hookCounts.onMounted  // 存取 reactive 物件的屬性，響應性完好

// 解構 reactive 物件的屬性 → 失去響應性 ❌
const { onMounted, onUpdated } = hookCounts
```

`toRefs` 解決的是「解構 reactive 物件的屬性」的問題。只要使用端不對 `hookCounts` 本身做解構，就不需要 `toRefs`。
