## 四、概念鞏固：用自己的話解釋

**Q1：為什麼 TypeScript 審查要從「型別定義層」開始，而不是從 vue-tsc 的錯誤訊息開始？**

> 因為型別定義層（interface、type）的錯誤會向上傳播。如果 `interface Option<T>` 的定義有問題，使用 `Option<T>` 的所有函式簽名和呼叫點都會出現紅線，這些紅線是「症狀」不是「根因」。
>
> 先修好定義層，使用端的誤報（因為定義錯誤傳播的紅線）自然消失，才能清楚看到真正的使用端問題。從 vue-tsc 的錯誤清單開始，可能改了一半發現都是同一個定義層問題造成的——浪費時間。

**Q2：功能驗收腳本為什麼要有「確認」項目，而不只是「操作」？**

> 「操作」描述你做了什麼，「確認」定義了成功的標準。沒有確認項目的測試無法判斷是否通過——你點了「登入」，但什麼叫做「對」？是看 console？看 DOM？看 Vue DevTools 的 data？
>
> 明確的確認項目讓測試可重複、可判斷，也是未來轉為自動化測試（`expect(...).toBe(...)`）的基礎。

**Q3：為什麼說 W5 PR 說明要寫「為什麼」而不是「是什麼」？請用一個具體例子說明差異。**

> **「是什麼」型說明**（差的）：
> 「新增 CustomSelect 元件，使用 generic="T" 語法實作泛型，並在 handleChange 中用 options.find 取得值。」
>
> **「為什麼」型說明**（好的）：
> 「CustomSelect 用 options.find 還原原始型別，是因為 HTML <select>.value 永遠是字串，直接 emit 會破壞泛型 T 的型別安全。若 T 是 number，用 select.value 時父元件會收到字串 "42" 而非數字 42，TypeScript 無法在編譯期攔截這個問題。」
>
> 第一種讓 reviewer 知道你「做了什麼」；第二種讓他們知道「這個選擇解決了什麼問題」，才有能力給出有意義的 Code Review 意見。
