## 四、概念鞏固：用自己的話解釋

**Q1：為什麼 usePagination 要求 `total` 是 `Ref<number>` 而非 `number`？**

A：因為 total 是「fetch 之後才知道的值」。API 回傳前 total = 0，fetch 完成後 total = 500。  
如果傳入 plain `number`，`totalPages = computed(() => Math.ceil(total / pageSize))` 中的 `total` 是函式呼叫當下的快照值——之後 fetch 結果回來改了外面的變數，computed 不知道，不會重算。  
傳 `Ref<number>` 後，computed 在執行時讀取 `total.value`，Vue 的依賴追蹤系統會記錄這個依賴——當 `total.value` 改變時，`totalPages` 自動重算，`hasPrev`/`hasNext`/`pageRange` 全部連帶更新。

**Q2：usePagination 和 useAsyncData 各自的「邊界」是什麼？如何在元件中銜接？**

A：邊界各自清晰：  
- `usePagination`：只管「現在第幾頁」、「共幾頁」、「有沒有上/下頁」。它不知道資料怎麼取，也不知道 fetch 的存在。  
- `useAsyncData`：只管「執行非同步函式、管理 loading/error/data 三態」。它不知道分頁的存在。

銜接由元件（或業務 Composable）負責：
```typescript
// 元件層
watch(pagination.currentPage, () => execute())
// fetch 函式讀取 pagination.currentPage.value，將 res.total 寫入 total.value
```
這樣兩個 Composable 之間零耦合，可以分別測試。

**Q3：省略號邏輯中用 0 代表「…」，這個設計好嗎？有沒有更好的選擇？**

A：用 0 代表省略號是「簡單有效」的做法，適合快速實作：數字天然不等於 0，在 `v-for` 中判斷 `p === 0` 邏輯清晰。  
更嚴謹的做法：定義 `type PageItem = number | 'ellipsis'`，用字串 `'ellipsis'` 取代 0。好處是型別更語意化，使用端不需要記住「0 代表省略號」這個約定，靜態分析也能在條件判斷時給予正確提示。  
實際產品中推薦使用字串版本；練習時 0 的版本更簡潔。

usePagination — UI 邏輯層
│
├── 設計邊界
│   ├── ✅ 管：currentPage / totalPages / hasPrev / hasNext / pageRange

│
├── 輸入
│   ├── total: Ref<number>   ← 必須響應式（fetch 後才確定）
│   ├── pageSize?: number     ← 靜態值，不需響應式
│   └── initialPage?: number
│
├── 核心計算（全部 computed，無副作用）
│   ├── totalPages = Math.ceil(total.value / pageSize)
│   ├── hasPrev = currentPage > 1
│   ├── hasNext = currentPage < totalPages
│   └── pageRange（省略號邏輯，最多 7 個項目）
│
├── 邊界保護
│   ├── goToPage → Math.max/min 防超出範圍

│

    ├── 與 useAsyncData（模式 A：元件 watch / 模式 B：業務 Composable 封裝）
