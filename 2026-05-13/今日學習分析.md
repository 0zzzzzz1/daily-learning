> `watchEffect` 的 `onCleanup` 為什麼比 `watch` 的 `onCleanup` 更容易觸發？

因為 `watchEffect` 自動追蹤執行過程中存取的**所有**響應式資料（不只是明確指定的 source），觸發重跑的機會更多。每次重跑前，上一次的 `onCleanup` 就會被呼叫——觸發來源越廣，清理越頻繁。

## 學習前 vs 學習後對照

| 概念 | 學習前認知 | 學習後認知 | 理解提升 |
|------|-----------|-----------|----------|
| `watchEffect` vs `watch` 本質差異 | 「watchEffect 自動追蹤，watch 要指定 source」（功能面的理解）| 除了依賴追蹤方式，還有：watch 能取得舊值、watchEffect 立即執行、依賴追蹤邊界在首個 await 前；這些差異**決定選用場景**，而不只是功能差異 | ⬆⬆⬆ 顯著 |
| `onCleanup` 的觸發時機 | 「元件卸載時才執行」（只知道 onUnmounted 配對）| **每次 effect 重跑之前**就觸發，元件卸載也觸發；watchEffect 因為重跑更頻繁，所以 cleanup 被呼叫次數遠多於 watch | ⬆⬆⬆ 顯著 |
| Race Condition 的根因 | 「非同步就會有 Race Condition」（模糊的恐懼）| 根因是「後發出的請求先回來，舊請求覆蓋新資料」；解法是在每次重跑前用 `controller.abort()` 取消前一個未完成的請求 | ⬆⬆⬆ 顯著 |
| `flush: 'post'` 的使用場景 | 「知道有這選項，不確定什麼時候用」| 當 watchEffect 的邏輯需要**讀取更新後的 DOM 狀態**（尺寸、滾動位置等）時，預設 `pre` 拿到的是舊 DOM，必須用 `post` | ⬆⬆ 明顯 |
| watchEffect 依賴追蹤邊界 | 「整個 async callback 都會追蹤依賴」（5/5 糾正過一次，今日鞏固）| await 之後的程式碼不被追蹤；實際模式是：在 await 之前讀取所有需要追蹤的響應式資料，儲存為本地變數 | ⬆ 鞏固加深 |
| Composable 中 watchEffect 的生命週期 | 「要手動 stop 才不會 memory leak」| Active Instance 機制：在 setup() 同步呼叫流中建立的 watchEffect 會隨元件卸載自動停止；只有在 setup 之外建立的才需要手動 stop | ⬆⬆⬆ 顯著 |

## 概念鞏固：用自己的話解釋

### Q1：什麼情境下選 `watchEffect`，什麼情境下選 `watch + immediate`？

這兩者都能在「建立時立即執行一次」，但選用依據不同：

**選 `watchEffect` 當**：
- 副作用邏輯會存取**多個**響應式資料，且這些依賴在執行前不一定都能列出來
- 不需要比較新舊值（只需要知道「發生了變化」）
- 例如：根據多個篩選條件 fetch 資料、根據多個設定值計算 DOM 樣式

**選 `watch + { immediate: true }` 當**：
- 明確知道要監聽**哪一個**（或哪幾個）響應式資料
- 需要比較新舊值（`watch(src, (newVal, oldVal) => {})`）
- 例如：當 `selectedId` 改變時切換選中狀態、當 `count` 超過閾值時發出通知

**心法**：`watchEffect` 是「先跑，邊跑邊學依賴」；`watch` 是「我知道我要看誰」。

### Q2：以下程式碼是否有 Race Condition？如何修正？

```ts
// 原始碼
watchEffect(async () => {
  const id = selectedId.value
  const data = await fetchUser(id)
  userProfile.value = data
})
```

**有 Race Condition**。如果：
1. `selectedId` 改為 1，發出 request-1（慢）
2. `selectedId` 改為 2，發出 request-2（快）
3. request-2 先回來，`userProfile` = user2 ✅
4. request-1 後來回來，`userProfile` 被覆蓋 = user1 ❌（顯示錯誤資料！）

**修正版**：

```ts
watchEffect(async (onCleanup) => {
  const id = selectedId.value
  const controller = new AbortController()

  onCleanup(() => controller.abort())

  try {
    const data = await fetchUser(id, { signal: controller.signal })
    userProfile.value = data
  } catch (err) {
    if (err.name !== 'AbortError') throw err
  }
})
```

當 `selectedId` 再次改變時，前一個 `controller.abort()` 會取消進行中的請求，確保舊請求不會覆蓋新結果。

### Q3：今天最重要的「概念鞏固」是什麼？

**`onCleanup` 是 effect 的「每次重跑前的善後」，而不只是「元件卸載時的善後」**。

這個認知升級很重要：把 `onCleanup` 理解為「卸載清理」是不完整的，會讓你漏掉「中途依賴改變時需要清理前一個副作用」的場景——這正是 Race Condition 防禦的關鍵時機。

正確的心智模型：每次 `watchEffect` 的 callback 執行，可以理解為「開一個工作」，`onCleanup` 是「下次工作開始前，關掉上一個工作」。元件卸載時，是最後一個「上一個工作」被關閉。
