### 3.2 W5 核心概念自我驗證

能以自己的話解釋以下概念，代表 W5 知識已真正內化：

**元件通訊核心原則**
> **Props Down / Events Up** — 資料從父流向子（Props），行為通知從子回傳父（Emits）。任何打破這個方向的設計都會降低可維護性。

**defineProps + withDefaults 的 TypeScript 邏輯**
> 三層架構：① `interface Props { ... }` 定義型別形狀；② `defineProps<Props>()` 讓 Vue 知道 Props 結構；③ `withDefaults(...)` 為 optional props（`?`）補上預設值，讓 TypeScript 不再把它們視為 `T | undefined`。

**v-model 展開原理**
> `v-model="val"` 等同於 `:modelValue="val"` + `@update:modelValue="val = $event"`。因此子元件不能直接修改 props（違反 Props Down），必須透過 emit 通知父元件更新。

**$attrs Fallthrough 的設計意圖**
> Vue 預設把所有未宣告的 attrs 套到根元素（Fallthrough）。`inheritAttrs: false` 停用預設，搭配 `v-bind="$attrs"` 手動指定目標，讓 `inputmode`、`autocomplete` 等 HTML 原生屬性透傳到 `<input>` 而非包裝用的 `<div>`。

**泛型元件（generic="T"）的核心價值**
> 讓 `<script setup>` 支援泛型型別參數，使 CustomSelect 能接受 `string | number` 等不同型別，同時保持 TypeScript 的型別安全。TypeScript 從 `v-model` 綁定值自動推導 T，無需使用者顯式指定。

### 4.1 `provide` / `inject` — 跨層資料傳遞

**解決的問題**：Props Drilling（祖孫元件間必須經由所有中間層傳遞 Props）

**核心機制**：
```typescript
// 祖先元件（或 App 層）
provide('key', value)

// 任意深度的後代元件
const value = inject('key')
```

**TypeScript 型別安全版本**：
```typescript
// 使用 InjectionKey 建立有型別的 key
import { provide, inject, InjectionKey } from 'vue'

const ThemeKey: InjectionKey<string> = Symbol('theme')

// 提供
provide(ThemeKey, 'dark')

// 注入（TypeScript 自動推導為 string | undefined）
const theme = inject(ThemeKey)
const themeWithDefault = inject(ThemeKey, 'light') // 有預設值則不含 undefined
```

**vs Props 的選用原則**：
- 直接父子通訊 → 用 Props/Emits（清晰、顯式）
- 跨多層共享的「主題/配置/服務」資料 → 用 provide/inject
- 全域應用狀態（多個頁面共享）→ Pinia（M6 主題）

**陷阱**：inject 的資料若不是 reactive，後代元件不會自動更新。通常 provide 要傳入 `ref` 或 `reactive` 物件。

---

### 4.2 Slots — 傳遞 UI 結構

**解決的問題**：有時父元件想決定子元件「內部顯示什麼」，不只是傳遞資料

**基礎 Slot（Default Slot）**：
```vue
<!-- 子元件 Card.vue -->
<template>
  <div class="card">
    <slot />  <!-- 父元件插入的內容出現在這裡 -->
  </div>
</template>

<!-- 父元件使用 -->
<Card>
  <p>這段內容由父元件決定</p>
</Card>
```

**具名 Slot（Named Slots）**：
```vue
<!-- Card.vue with named slots -->
<template>
  <div class="card">
    <header><slot name="header" /></header>
    <main><slot /><!-- default --></main>
    <footer><slot name="footer" /></footer>
  </div>
</template>

<!-- 父元件使用 -->
<Card>
  <template #header>標題文字</template>
  主要內容
  <template #footer>頁尾</template>
</Card>
```

**Scoped Slots（作用域插槽）** — 子元件把資料傳回給父元件決定渲染方式：
```vue
<!-- List.vue -->
<template>
  <ul>
    <li v-for="item in items" :key="item.id">
      <slot :item="item" />  <!-- 把 item 傳給父元件的 slot template -->
    </li>
  </ul>
</template>

<!-- 父元件：決定每個 item 怎麼渲染 -->
<List :items="tasks">
  <template #default="{ item }">
    <span :class="{ done: item.done }">{{ item.text }}</span>
  </template>
</List>
```

### 4.3 動態元件 `<component :is>`

**解決的問題**：哪個元件要顯示，由資料（而非程式碼結構）決定

**基本用法**：
```vue
<template>
  <!-- is 傳入元件物件（推薦）或元件名稱字串 -->
  <component :is="currentComponent" />
</template>

<script setup lang="ts">
import TabA from './TabA.vue'
import TabB from './TabB.vue'

const tabs = { a: TabA, b: TabB }
const activeTab = ref<'a' | 'b'>('a')
const currentComponent = computed(() => tabs[activeTab.value])
</script>
```

**vs `v-if` 的選用原則**：
- 少數（2–3 個）固定元件切換 → `v-if` 更清晰
- 元件清單由設定或路由驅動、或未來可能動態擴充 → `<component :is>` 更彈性

**`<KeepAlive>` 搭配**：保留切換前的元件狀態（如 Tab 切換後返回仍有輸入值）：
```vue
<KeepAlive>
  <component :is="currentComponent" />
</KeepAlive>
```

## 六、自我檢核問題（W5 完整知識驗證）

以下 5 個問題，若能不查文件回答，代表 W5 真正學會：

**Q1**：`withDefaults` 的作用是什麼？少了它 TypeScript 會如何看待 `label?: string` 的 prop？

> **參考答案**：少了 `withDefaults`，TypeScript 視 `label` 的型別為 `string | undefined`，每次使用都需要空值防禦（`label?.length` 或 `label ?? ''`）。`withDefaults` 提供預設值後，TypeScript 知道「取到元件內部時一定有值」，型別縮窄為 `string`，不再含 `undefined`。

**Q2**：為什麼 `<select>` 元素的 `.value` 永遠是 `string`，即使 option 的 value 是 `number`？

> **參考答案**：這是 HTML 規範限制——所有 HTML 屬性的值本質都是字串；即使 `:value="42"` 在 DOM 中也會被序列化為 `"42"`。因此 CustomSelect 在 `@change` handler 中必須用 `options.find(opt => String(opt.value) === event.target.value)` 還原原始型別 T。

**Q3**：`$attrs` 包含哪些內容？什麼時候需要 `inheritAttrs: false`？

> **參考答案**：`$attrs` 包含所有「未被 `defineProps` / `defineEmits` 宣告」的屬性，包括 `class`、`style`、`id`、HTML 原生屬性（`inputmode`、`autocomplete` 等）和事件監聽器（`@click` 等）。  
> 需要 `inheritAttrs: false` 的情況：當根元素不是你想套用 attrs 的目標時（如包裝用的 `<div>` 不應該接收 `inputmode`，而是內部 `<input>` 應該接收）。

**Q4**：`validate()` 為什麼設計成回傳 `boolean` 而不是 `void`？

> **參考答案**：回傳 `boolean` 讓呼叫端（`handleSubmit`）可以 `if (!validate()) return` 立即停止提交流程。若 `validate()` 回傳 `void`，呼叫端必須另外讀取 `errors` 物件的狀態再判斷——耦合度更高，且需要了解 `errors` 的結構。回傳 `boolean` 是「問一個問題：通過了嗎？」的語意，更清晰。

**Q5**：`provide/inject` 和 Pinia 有什麼差異？什麼情況下各自更適合？

> **參考答案**：
> - `provide/inject` 是「元件樹內的局部共享」，作用域限於提供者的子樹；適合元件庫內部的主題/配置注入（如 `<Form>` 提供 disabled 狀態給所有 `<Field>` 子元件）
> - Pinia 是「應用層級的全域狀態管理」，跨頁面、跨元件樹共享；適合用戶資訊、購物車、通知等整個應用都需要存取的狀態
> - 判斷標準：若狀態只在某個元件子樹中有意義 → provide/inject；若多個不相關的頁面都需要這份狀態 → Pinia
