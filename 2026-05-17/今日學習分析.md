> 你有 `useLifecycleLogger.ts`、`useWatchEffectLogger.ts`、`LifecycleLogger.vue` 三個檔案。TypeScript 型別審查的順序和重點應該是什麼？有哪些地方是最容易遺漏型別的？

**答**：審查順序應從「型別定義層」往「使用層」進行，原因是定義層的錯誤會向上傳播影響所有使用端，先修定義才能正確判斷使用端的問題。本作業的高風險遺漏點包括：

| 風險點 | 問題描述 | 正確做法 |
|--------|---------|---------|
| `LifecycleLog.hook` 型別 | `hook: string` 太寬泛 | `hook: keyof HookCounts` 精確約束 |
| `record()` 參數型別 | `hookName: string` 無法保證合法 key | `hookName: keyof HookCounts` |
| `Object.keys` 回傳型別 | 固定 `string[]`，不能直接當 index | `as Array<keyof HookCounts>` 斷言 |
| `FlushMode` 型別 | `Ref<string>` 允許任意字串 | `type FlushMode = 'pre' \| 'post'` |
| `hookColorClass` 參數 | 接受 `string` 太寬泛 | 接受 `keyof HookCounts` |
| Composable 回傳型別 | 依賴推導，無 API 契約 | 顯式標注回傳型別 |

## 概念鞏固：用自己的話解釋

### Q1：TypeScript 型別審查為什麼要從「定義層往使用層」？

因為型別定義是整個系統的「地基」。如果 `HookCounts` 的定義有問題，所有使用 `hookCounts` 的程式碼都可能藏著錯誤——但因為 TypeScript 推導是從定義層往上傳播的，錯誤的定義有時不會在使用端顯現出來，或者顯現出來的錯誤讓人摸不著頭緒。

相反地，如果先從正確的定義出發，TypeScript 的型別推導會幫你驗證所有使用端是否一致。就像蓋房子先確認地基，才知道牆和屋頂有沒有對齊。

### Q2：`Object.keys(hookCounts)` 回傳 `string[]`，但我們需要的是 `Array<keyof HookCounts>`。這個設計限制的原因是什麼？

這是 TypeScript 刻意的保守設計。在執行期，JavaScript 物件可能被擴充屬性（例如在 runtime 中加了 `hookCounts['extraKey'] = 0`）。TypeScript 的靜態分析無法保證執行期的物件只有型別定義中的 key，所以 `Object.keys` 被設計成永遠回傳更寬泛的 `string[]`，而不是狹窄的 `Array<keyof T>`。

在我們這個場景，`HookCounts` 的結構是固定的（8 個 hook，不會動態增加），所以 `as Array<keyof HookCounts>` 的斷言是安全的——我們比 TypeScript 更了解這個物件的結構。

### Q3：為什麼 Composable 的回傳型別要顯式標注，而不是讓 TypeScript 自動推導就好？

自動推導對使用端來說是「黑盒」。使用端必須跳進實作才知道 Composable 回傳了什麼；如果實作被大幅修改，回傳型別悄悄改變，TypeScript 不會提醒你。

顯式標注的回傳型別是「API 契約」——它說「我保證這個 Composable 永遠回傳這些東西，形狀如此，型別如此」。如果實作被改動但回傳的東西與標注不符，TypeScript 在 Composable 內部就報錯，而不是讓錯誤靜默傳播到所有使用端。這是工程上更負責任的做法。
