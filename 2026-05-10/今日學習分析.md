## 概念鞏固：用自己的話解釋

**Q1：為什麼 Composable 的回傳型別要明確標注，不能只靠 TypeScript 自動推導？**

**A：**

TypeScript 自動推導是可以的，程式能正確執行。但明確標注有兩個額外價值：

1. **當作 API 契約**：明確告訴使用端「這個 Composable 提供什麼」。未來如果改動 `useTasks` 的實作，TypeScript 會在回傳型別和實作不符時立刻報錯，而不是讓使用端悄悄地拿到錯誤的型別。

2. **文件即程式**：從回傳型別就能知道 Composable 的完整 API 界面，reviewer 不需要讀完整個實作才能理解用法。

類比：API 文件比「你去看 source code 吧」更友善。

---

**Q2：PR 說明應該著重「是什麼」還是「為什麼」？**

**A：**

重點在**「為什麼」**。

「是什麼」（功能列表）在 commit 歷史和 diff 裡就能看到。reviewer 真正需要的是「你做了哪些設計選擇，以及選擇的理由」——這讓 reviewer 可以評估：
- 你的選擇是否考慮了正確的 trade-off？
- 有沒有你沒有考慮到的邊界情況？
- 這個設計在未來擴展時會不會有問題？

如果 PR 說明只有功能列表，reviewer 無從判斷設計品質，只能說「程式能跑」，而不是「設計是好的」。

---

**Q3：最終驗收腳本比「手動點一點試試看」好在哪裡？**

**A：**

「手動點一點試試看」的問題是**覆蓋率不確定**——每次測試都可能漏掉不同的功能路徑，不知道自己是否覆蓋了所有邊界情況。

系統化的驗收腳本：
- 每個步驟都有明確的「確認：XXX」，讓你知道「什麼叫做通過」
- 按順序執行，確保每條功能路徑（基本功能、字數限制、持久化、空狀態）都被測試到
- 可以在開 PR 前重複執行，確保每次都一致

這就是 Unit Test 還沒引入前的「手動測試規格書」。當 M5 學習 Vitest 時，這個腳本的每個步驟就會自然地轉化成一個 test case。

## 今日反思

1. **「能跑」和「可以被 Review」的距離**：今天的工作讓我認識到，一個完整的軟體開發任務不只包含「讓功能正確運作」，還包含「讓程式碼能夠被他人理解和評估」。型別完整、commit 清晰、PR 說明充分——這些是專業度的體現，也是真實職場的標準。

2. **TypeScript 型別審查是習慣，不是補救**：今天把 `any` 找出來並修掉，花的時間遠比「一開始就寫好型別」要多。未來的開發習慣調整：在撰寫函式時就同步標注回傳型別，而不是等完成後再補。

3. **PR 說明是與 reviewer 的對話起點**：「你想要 reviewer 關注什麼？」這個問題決定了 PR 說明的重點。如果不說明設計決策，reviewer 可能只關注語法格式，而忽略了更重要的架構問題。把「為什麼」寫進 PR，是主動引導 review 品質的方式。
