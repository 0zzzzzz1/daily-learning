## 概念鞏固：用自己的話解釋

### Q1：W3 的核心設計原則是什麼？

**Composable 將「狀態與邏輯」從「UI 渲染」中完全解耦**。

`useTasks.ts` 只管理 State（`tasks`, `filterMode`），Computed（`filteredTasks`, `totalCount`, `doneCount`），Watch（寫入 localStorage），和 Methods（CRUD 操作）。它不知道也不在乎自己被哪個元件使用、用什麼樣式呈現。

`TaskList.v2.vue` 只負責「把 Composable 回傳的資料渲染出來」，並把使用者的操作委派回 Composable。

這樣的分離讓：(1) 邏輯可以被測試（不需要掛載 DOM）；(2) UI 可以被替換（換成 Mobile 版只需換元件，不需動 useTasks）。

### Q2：`watch` 和 `onMounted` 在持久化回路中為什麼不可互換？

它們的職責是**時間點和方向完全相反的對稱設計**：

- `watch(tasks, saveToStorage)` → **寫**：「只要 tasks 有變化，把最新狀態存到 localStorage」
- `onMounted(() => loadFromStorage())` → **讀**：「元件第一次掛載時，把 localStorage 的資料讀進來」

若把 `watch` 改成 `{ immediate: true }`，**第一次執行 handler 時 `tasks` 是空陣列（初始值），會立刻覆蓋掉 localStorage 裡的資料**。而 `onMounted` 在所有 Composable 初始化完成後才執行，時機正確。

### Q3：W3 整週學到最重要的一件事是什麼？

> **「能跑」和「可 Review」之間有一段距離，而這段距離就是工程師專業度的一部分。**

W3 最後兩天花在型別審查、PR 說明、功能驗收腳本——這些東西不讓程式「跑得更快」，但它們讓程式碼「對他人有意義」。`as T` 和型別守衛的差別、PR 說明的「為什麼」、16 步驟驗收腳本，都是「讓程式碼能被信任」的工程實踐。
