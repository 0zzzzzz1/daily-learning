## 昨日問題解答

> **問題**：W4 作業 PR 說明中，Reviewer 追問：「如果未來要增加 `onErrorCaptured` hook，`HookCounts` 型別、`resetAll`、以及 Composable 回傳型別，分別需要改哪些地方？改動成本大嗎？」

**答**：

改動清單如下：

| 位置 | 需要修改嗎？ | 具體修改 |
|------|:----------:|---------|
| `HookCounts` 型別定義 | ✅ 是 | 加一行：`onErrorCaptured: number` |
| 初始值物件（`hookCounts` 的初始 reactive）| ✅ 是 | 加一行：`onErrorCaptured: 0` |
| `record()` 函式本體 | ❌ 否 | `hookName: keyof HookCounts` 自動包含新 key |
| `resetAll()` 函式本體 | ❌ 否 | `Object.keys(hookCounts) as Array<keyof HookCounts>` 動態迭代，自動涵蓋新 key |
| `onErrorCaptured` hook 登錄（呼叫點）| ✅ 是 | 在 `setup` 中加：`onErrorCaptured(() => record('onErrorCaptured'))` → 1 行 |
| Composable 回傳型別顯式標注 | ✅ 是（小改）| 若標注了 `hookCounts` 的形狀，TypeScript 會提示需補上新 key；若整體回傳 reactive 物件，推導自動更新 |

**結論**：改動成本**極低**，核心修改只有 3 處（型別定義 + 初始值 + 呼叫點），合計約 3–4 行。`resetAll` 的 `Object.keys` 動態設計使得「新增 hook 不需改清零邏輯」，這正是在型別定義層做好設計的好處。

這也說明了**可擴充性的設計原則**：把「什麼是合法值」集中在型別定義層（`HookCounts`），把「對所有合法值的操作」設計成動態迭代（`Object.keys as Array<keyof T>`），新增成員時只需改定義層，操作層自動跟上。

## M2 銜接預習：元件通訊基礎

### 為什麼從 Props / Emits 開始？

W4 把單一元件的「時間維度」學完了（生命週期 × 響應式 × Composable）。M2 要打開「空間維度」——多個元件如何協作。Props 和 Emits 是 Vue 元件通訊的**基本契約**，所有進階通訊（v-model、Slots、provide/inject）都建立在這個基礎上。

### `defineProps`

在 `<script setup>` 中，`defineProps` 取代了 Options API 的 `props` 選項：

```vue
<script setup lang="ts">
// 方式 1：Runtime 宣告（簡單）
const props = defineProps({
  title: { type: String, required: true },
  count: { type: Number, default: 0 },
})

// 方式 2：TypeScript 型別宣告（推薦，與 TS 整合更好）
const props = defineProps<{
  title: string
  count?: number
}>()

// 方式 2 加上預設值（需搭配 withDefaults）
const props = withDefaults(defineProps<{
  title: string
  count?: number
}>(), {
  count: 0,
})
</script>
```

**關鍵特性**：
- Props 是**單向資料流**：父 → 子，子不應該直接修改 props
- 在模板中直接使用 `title`，在 script 中需要 `props.title`
- `defineProps` 是編譯器巨集（compiler macro），不需要 `import`

### `defineEmits`

```vue
<script setup lang="ts">
// Runtime 宣告
const emit = defineEmits(['update:modelValue', 'close'])

// TypeScript 型別宣告（推薦）
const emit = defineEmits<{
  'update:modelValue': [value: string]  // Vue 3.3+ 具名 tuple 語法
  close: []
}>()

// 使用
emit('update:modelValue', newValue)
emit('close')
</script>
```

**關鍵特性**：
- Emits 是子 → 父的**事件通知**，不是直接修改父狀態
- 用 TypeScript 型別宣告可以精確約束事件的 payload 型別
- `defineEmits` 同樣是編譯器巨集

### `v-model` 進階

`v-model` 本質上是 Props + Emits 的語法糖：

```vue
<!-- 父元件使用 -->
<MyInput v-model="text" />

<!-- 等同於 -->
<MyInput :modelValue="text" @update:modelValue="text = $event" />
```

子元件實作：

```vue
<script setup lang="ts">
const props = defineProps<{ modelValue: string }>()
const emit = defineEmits<{ 'update:modelValue': [value: string] }>()
</script>
<template>
  <input :value="props.modelValue" @input="emit('update:modelValue', $event.target.value)" />
</template>
```

**進階：多個 v-model**（Vue 3 新特性）：

```vue
<!-- 父元件 -->
<UserForm v-model:name="userName" v-model:age="userAge" />

<!-- 子元件 Props/Emits -->
defineProps<{ name: string; age: number }>()
defineEmits<{
  'update:name': [value: string]
  'update:age': [value: number]
}>()
```

### W4 PR 說明核心：設計決策的「為什麼」

PR 說明應涵蓋以下 3 個設計決策說明（這是 Reviewer 最需要理解的部分）：

**決策 1：triggerUpdate 為什麼用 `ref`（而非按鈕直接觸發）**
> `triggerUpdate` 是 `ref<number>(0)`，每次 `triggerUpdate.value++` 時，Vue 偵測到值改變，才能在 `watchEffect` 中建立依賴——讓 Reviewer 看到「讀取建立依賴」的因果鏈。若改用函式直接修改 DOM，watchEffect 無法追蹤，`onUpdated` 也不會觸發。

**決策 2：`hookCounts` 用 `reactive`，`logs` 用 `ref`**
> `hookCounts` 結構固定（8 個 hook）+ 整體回傳（不需解構）+ 逐項更新（不整批替換）→ `reactive` 語義最清晰。`logs` 需要整批替換（`clearLogs` 替換為 `[]`）→ `ref` 整批替換語義明確。

**決策 3：flush 動態切換為什麼要停止舊 effect 並建立新 effect**
> Vue 的 flush 選項在 effect 建立時就固定進了 scheduler，無法在執行期修改。動態切換的唯一方式：`stop()` 舊 effect → 用新 flush 值 `watchEffect(callback)` 建立新 effect。這個邏輯封裝在 `useWatchEffectLogger` 內部，使用端只需改 `flushMode.value`，介面乾淨。

## 自我檢核問題（W4 整週）

**Q1**：`onMounted` 和 `watch({ immediate: true })` 都能在元件初始化時執行邏輯，這兩者的適用場景有什麼根本差異？

**Q2**：`watchEffect` 的 `onCleanup` 在以下哪個時機觸發？
- (A) 只在元件卸載時
- (B) 每次 effect 重跑之前
- (C) 每次 effect 重跑之後

**Q3**：下面的 `toRefs` 使用有什麼問題？

```ts
const name = ref('Alice')
const age = ref(30)
const { nameRef, ageRef } = toRefs({ name, age }) // 這樣對嗎？
```

**Q4**：同一個元件中使用兩個 Composable，它們各自在 `setup()` 內呼叫的 `onUnmounted` 會怎樣？

**Q5**：`type FlushMode = 'pre' | 'post'` 比 `string` 好在哪裡？舉一個 TypeScript 在編譯期幫你抓到錯誤的例子。

---

## 參考答案

**A1**：`watch({ immediate: true })` 以響應式資料的「當前值」觸發初次執行，適合「初次執行邏輯與後續回應相同」的場景。`onMounted` 在 DOM 掛載完成後觸發，適合「需要讀取 DOM 狀態、localStorage、或者明確要區分『首次啟動』與後續響應」的場景。後者不能被前者取代，因為 `immediate: true` 的初次觸發早於 DOM 就緒。

**A2**：**(B) 每次 effect 重跑之前**。`onCleanup` 登錄的函式在「下次 effect 執行之前」觸發（用於清理上一輪的副作用），以及在元件卸載時最後一次觸發。這讓它成為取消上一個 fetch、清理計時器、abort 請求的理想位置。

**A3**：問題：`{ name, age }` 是普通物件（非 `reactive()` 物件），對普通物件使用 `toRefs` 結果不會是響應式的 ref。正確做法：直接使用 `name` 和 `age`（它們本身已經是 `ref`，不需要 `toRefs` 包裝）。`toRefs` 的前提是「對 `reactive()` 建立的響應式物件的屬性建立連動 ref」。

**A4**：兩個 Composable 各自在 `setup()` 同步流中呼叫 `onUnmounted`，都綁定到同一個 Active Instance（當前元件）。元件卸載時，按登錄順序各自獨立觸發，彼此不干擾。這是 Composable 封裝生命週期邏輯的核心能力。

**A5**：`FlushMode` 讓 TypeScript 在編譯期拒絕：
```ts
flushMode.value = 'sync'  // ❌ Type '"sync"' is not assignable to type 'FlushMode'
flushMode.value = 'async' // ❌ 同上
```
`string` 型別的話，這些錯誤值只會在執行期才暴露（Vue 的 `flush` 選項不接受 `'sync'` 是另一個值，`'async'` 不存在），TypeScript 不會提前攔截。
